# In-game co-op integration

The Windows mod should let players launch Project Silverfish through Steam, choose **Host Co-op** or **Join Co-op** on the title screen, and manage the session in the game. The host selects or creates a campaign and chooses the Direct IP UDP port. A guest imports a host-issued invite, reviews the endpoint, and selects or creates a character owned by that host campaign. The menu shows admission, world loading, reconnect grace, and save status as separate states.

The [18 locked rules](DESIGN.md) apply to every milestone. Moving the controls into the game leaves the host responsible for the shared world, wallet, travel, rewards, and committed campaign. Direct IP is the first transport. Steam Invite remains deferred and will use the same campaign identities and admission rules.

## Current boundary

The stock title map `/Game/Classes/Maps/MainMenu_P` opens `/Game/Classes/GUI/MainMenu_Widget.MainMenu_Widget_C` through the local `PlayerControler_FP_C:OpenMenu` call. This gives the mod a specific world, controller, and widget to qualify before adding its own controls. Install the controls once per live title widget and remove them when the widget or world changes. Keep the stock New Game, Continue, and Load bindings in place.

The current Python launcher starts a staged game process with `-userdir` and `-MULTIHOME=127.0.0.1` before Unreal initializes. The public Direct IP port belongs to the authenticated QUIC transport. The invitation pins the host identity, and admission checks the participant credential, character ownership, and game and mod fingerprint before forwarding Unreal traffic over loopback. The host checkpoints a versioned `campaign.json` and backup alongside verified stock SaveGame generations for the host and detached characters. ## Delivery milestones

1. **Title menu to isolated co-op stage.** Add the title entry in the matched staged build. Host and Join call the current supervisor through a private, structured handoff. The supervisor reserves the campaign or profile, passes an isolated prelaunch user directory, and reports when the requested host or guest is ready. Start with two staged processes. Verify one click produces one launch, a rejected or cancelled request leaves the title usable, and stock single-player buttons still load their own data. Hash the original save directory before and after.
2. **Steam startup and complete in-game controls.** Qualify the same menu entry on an ordinary Steam launch. Package the runtime used by the handoff so players can host, import an invite, select a character, reconnect, and leave without opening a terminal. Resolve whether Steam and the executable can coexist with the isolated child. If a process handoff is needed, perform it at the title screen and confirm child readiness. On two separate PCs, verify a player-selected port, an authenticated join, movement, automatic reconnect to the same character after packet loss, and host restart. Include a wrong-build invite, a rejected credential, and a cancelled launch.
3. **In-process session supervisor and transport.** Give the shipped Windows mod runtime ownership of admission, reconnect reservations, Unreal relay management, and state reporting. First test an embedded runtime for the existing QUIC coordinator so the initial handoff can preserve invitations, credentials, and reconnect semantics. Keep the transport on its worker thread and apply Unreal mutations on the game thread. Bind raw Unreal gameplay to loopback. Repeat admission, timeout, network-loss, active roster, hot join, zone travel, and wipe checks on two PCs.
4. **Native campaign persistence.** Move the checkpoint coordinator, campaign lock, and recovery into the native runtime. Preserve stock serialization for typed native state and commit a versioned manifest that binds the host world, guests, wallet, checkpoints, and item and reward receipts to one generation. Keep a verified backup and resume the last complete commit after interruption. Test existing co-op campaign migration, termination during each commit phase, recovery after a partial write, and replay of a previously settled transaction.
5. **Keep mode selection save-safe.** A self-contained release can relaunch Project Silverfish from the title screen with the co-op profile selected before Unreal initialization. Verify that the original process can exit after confirming the isolated session starts. Reuse the running game process only after proving that cached engine paths, menu listing, existence, load, save, autosave, delete, restore, shutdown, and Steam Cloud all use the selected profile across repeated mode changes and crashes.

## Release and local control

Ship a matched Windows loader, native mod, scripts, and the redistributable dependencies needed by the selected milestone. Use the player's local Steam installation for stock game content. The package and repository contain mod assets and code. Stock packages, extracted assets, user saves, host keys, and invitations stay local.

Keep a local, versioned JSON interface alongside the menu. It should expose session and map state, the active and reserved roster, checkpoint revision and recovery status, and supported player actions. Commands carry request IDs and the current session generation so an AI can distinguish an accepted request from an applied or durably committed result. Keep control files local to the Windows account and redact invite credentials and private keys from normal status and events. Use the same host validation for a menu action and its documented JSON equivalent. [Current local control](../tools/silverfish/control.py)
