# Native integration status

The staged loopback build has one host and one guest. The campaign store, guest catalog, action channel, and checkpoint format are active in both playtest maps. See the [locked design](DESIGN.md) for release requirements.

| Area | Verified or implemented in the staged build | Work before campaign play |
| --- | --- | --- |
| Hosting and players | Authenticated Direct IP, guest-owned character selection, native replicated movement, reconnect and host restart | More than one guest, real-network validation, and Steam Invite |
| Combat and respawn | Fixture damage, crouch and speed restrictions, revive, locked wipe, and checkpoint placement. The C++ lab processes stock lethal damage and revives a guest on the same pawn. Its native health persists across reconnect, playtest travel, and host restart. | Host native death integration, weapon and NPC damage validation, friendly-fire routing, native HUD and the full respawn flow |
| Loot and inventory | Replicated toy pickup, one committed winner, independent durable co-op inventory, and owner-only bag contents. The C++ lab verified a native inventory item value copy using a staged Bandage. | Stock item and equipment routing, native inventory persistence, trait-aware native loot rolls, and visual backpack actors |
| Wallet, shops, and quests | Shared wallet transaction, native cash projection, read-only placed shop offers, and native start/read-back for one authored quest | Native shop checkout and dialogue, stock objective routing, and end-to-end quest turn-in rewards |
| World and travel | Authoritative scene snapshots and host-led authenticated travel between the two playtest maps | Native new-game setup and restoration, clock and weather projection, and a gate on real zone boundaries |

The cooked game uses the same game-instance save reference for both server-side pawns by default. A live probe moved the guest to a distinct transient SaveGame object and read 125 guest HP with the host still at 250 HP. Native inventory and dialog logic still calls the shared GameInstance or player/controller index zero. Replacing the save reference alone leaves those call sites shared.

The local death overlay qualifies one exact cooked build and changes the common Blueprint death function. A matched UE4SS v4.0.0 loader and C++ add-on reproduced the lethal-damage result on a stock-package stage through a pre-call hook. The supervised C++ lab then kept a distinct live guest save between game ticks. The guest took stock lethal damage from 250 to −1 HP, entered the co-op downed state, and revived in place at 25 HP. The host remained at 250 HP. The same guest character kept 25 HP across host-led travel and restart. The lab uses a deterministic damage call, with the scope already active when damage arrives. An engine connection teardown between interception and event delivery still needs validation. [Native build and lab instructions](../native/README.md) · [UE4SS build guide](https://github.com/UE4SS-RE/RE-UE4SS/blob/v4.0.0/docs/guides/creating-a-c%2B%2B-mod.md)

Stock exits pass through `Level_Exit_BP_C.ActivateLevel`, `GameInstance_FP.Prep_OpenNextLevel`, and `GameInstance_FP.LoadNextLevel`. The final Blueprint opens the next map with empty travel options. The earliest player-specific ordinary exit event exposes the overlapping actor, and the dungeon door interaction exposes the initiating player. Both are candidates for redirecting natural transitions through the existing host travel gate. Physical boundary collision and exit-specific entrance placement still need implementation.

The stock Silverfish build ships Unreal's Null subsystem. A Steam Invite test needs an authorized Steamworks integration under the game's App ID and two separately entitled Steam sessions for a real invite round-trip. The existing Direct IP path supports local two-process testing without Steam.
